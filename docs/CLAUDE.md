# CLAUDE.md — TriadeFlow Dashboard Repository Guide

**For: AI assistants, agents, and colleagues reviewing this codebase**

This file describes the repo structure, conventions, and key decisions so you can work effectively on this project.

## Quick Facts

- **Language**: TypeScript (strict mode)
- **Monorepo**: pnpm workspaces + Turbo
- **Reference Dashboard**: [Salus](https://salus.triadeflow.com.br) (legacy, single-tenant, SQLite-based — this project is the modern rewrite)
- **Model Layers**: `raw → stg → mart → metric` (dbt-core, similar to talentus-v2)
- **Frontend**: Next.js 14 (App Router), hosted on Cloudflare Pages
- **Workers**: Cloudflare Workers + Queues (NOT Docker/BullMQ — important constraint!)
- **Database**: Supabase (Postgres), one per client
- **Metrics**: YAML catalog (not hardcoded, unlike salus-live's 421-line bi.js disaster)

## Repository Structure

### `apps/web` — Next.js Dashboard Frontend
- **Route structure** mirrors Salus navigation:
  - `app/(dashboard)/painel/` — overview
  - `app/(dashboard)/trafego/` — Meta Ads traffic
  - `app/(dashboard)/criativos/` — Ad creatives
  - `app/(dashboard)/funil/[stage]/` — funnel drill-down
  - `app/(dashboard)/metricas/` — metrics catalog + custom builder
  - `app/(dashboard)/auditoria/` — sync logs, freshness checks, schema drift
  - `app/(dashboard)/settings/` — branding, user roles
  - `app/api/` — edge functions for custom metrics, module config, etc.

### `apps/workers` — Cloudflare Workers (Ingestion)
- **NOT a Node.js server** — runs on Cloudflare's V8 isolate, no long-lived connections, no Python
- **Purpose**: Cron-triggered producers enqueue messages; consumers process queue, call external APIs, write to raw tables
- Structure:
  - `src/scheduler/` — cron triggers per module
  - `src/modules/{ghl,meta-ads,etc}/` — producer + consumer per module
  - `src/lib/retry.ts` — backoff + retry logic for transient errors
  - `src/lib/raw-writer.ts` — Drizzle client for writing to raw.* tables (uses Cloudflare Hyperdrive for pooled Postgres)

**Constraint**: dbt-core (Python) cannot run in Workers → it runs in GitHub Actions instead (see below).

### `packages/db` — Drizzle Schema + Migrations
- **Source of truth** for all table definitions (raw, stg, mart, config, audit schemas)
- Generated by Drizzle Kit; migrations live in `drizzle/migrations/`
- Used by:
  - Frontend (reading mart/metric via Drizzle client)
  - Workers (writing to raw via service-role key + Hyperdrive)
  - dbt (raw/config tables inform stg/mart modeling)

**Key schemas**:
- `raw.*` — append-mostly, includes `_ingested_at`, `_source_batch_id`, `_raw_payload jsonb` for full audit trail
- `config.*` — `module_registry`, `client_config`, `custom_metrics`, `branding_theme`, `user_roles`
- `audit.*` — `sync_run_log`, `dbt_run_log`, `_schema_drift_log`, `freshness_check_log`

### `packages/metrics-catalog` — YAML Metrics + Codegen
- **Canonical source** of all metrics (not the codebase, not the database)
- Structure:
  - `catalog/primary/*.yml` — universal metrics (CAC, leads, conversion rate, etc.)
  - `catalog/secondary/*.yml` — module-dependent metrics (CTR only if Meta Ads enabled)
  - `catalog/modules/{ghl,meta-ads}/` — module-specific metrics
  - `catalog/custom/<client-slug>/` — client-specific metrics (generated from UI)
  - `schema/metric.schema.json` — JSON Schema validating all YAML entries
  - `src/load.ts` — catalog loader + validator
  - `src/generate-dbt-models.ts` — **important** — emits `transform/models/metric/generated/*.sql` + `schema.yml` from YAML, runs before `dbt run`

**Why YAML instead of hardcode?** → Salus-live had 421 lines of metric calculations in bi.js, impossible to audit or modify safely. Here, metrics are declarative and single-source-of-truth.

### `packages/modules-registry` — Central Module Registry
- `src/registry.ts` — array of `ModuleDefinition` (ghl, meta-ads, extensible for future)
- Each module declares: id, display name, raw table schema, dbt path, metrics catalog path, sync worker, required secrets, dashboard sections
- Read by:
  - Workers → know which modules to sync
  - dbt codegen → know which metrics to materialize
  - Frontend → know which nav sections to show

**Adding a new module** (e.g., Google Ads):
1. Add entry to `MODULE_REGISTRY` in `packages/modules-registry/src/registry.ts`
2. Create raw table schema in `packages/db/src/schema/raw` (e.g., `google_ads.ts`)
3. Create Worker producer+consumer in `apps/workers/src/modules/google-ads/`
4. Create dbt stg models in `transform/models/stg/google_ads/`
5. Create metrics YAML in `packages/metrics-catalog/catalog/modules/google-ads/`
6. Document in [MODULE_AUTHORING_GUIDE.md](./MODULE_AUTHORING_GUIDE.md)

### `packages/theme` — Design Tokens
- `src/tokens.ts` — `ThemeTokens` interface (colors, typography, spacing, shadows, etc.)
- `DEFAULT_THEME` — TriadeFlow brand defaults (Indigo, Cyan, etc.)
- `generateCSSVariables()` — turns tokens into CSS custom properties (used by Next.js at runtime)
- **Per-client override**: `config.branding_theme` table stores client-specific colors/logo extracted at kickoff

### `transform/` — dbt-core Project (Transformation)
- **Runs in GitHub Actions**, not in Workers (Python interpreter needed)
- Scheduled per `client_config.dbt_schedule` (e.g., every 20 minutes)
- Layers:
  - `models/stg/` — 1:1-ish cleaned views per raw source (e.g., `stg_ghl__contacts`, `stg_meta_ads__ad_insights`)
  - `models/mart/` — business-conformed tables (e.g., `mart_leads`, `mart_spend`, `mart_funnel_events`)
  - `models/metric/generated/` — codegen output from metrics-catalog (one SQL per metric)
- **Tests**:
  - Generic: `not_null`, `unique`, `accepted_range` (applied via `tests:` field in YAML)
  - Singular: custom tests in `tests/`, e.g., "sum of leads by funnel_stage == total leads"
  - Freshness checks: per raw source, thresholds from `sync_schedule`
- **Macros**:
  - `filter_safe.sql` — prevents divide-by-zero in aggregations (talentus pattern)
  - `schema_drift_check.sql` — detects upstream API field changes, logs to `audit._schema_drift_log`

### `scripts/onboarding/` — Replication CLI
- `cli.ts` — interactive `pnpm onboard new-client` command
- `steps/01-*.ts` through `steps/07-*.ts` — each step (provision Supabase, run migrations, configure modules, etc.)
- **Goal**: intern-readable, one-command client setup

### `docs/`
- **CLAUDE.md** (this file) — repo map for AI assistants
- **ARCHITECTURE.md** — design decisions, tradeoffs, why dbt isn't in Workers
- **ONBOARDING_RUNBOOK.md** — human-readable client setup guide (screenshots, troubleshooting)
- **MODULE_AUTHORING_GUIDE.md** — how to add a new module
- **METRICS_CATALOG_GUIDE.md** — YAML schema reference, filter-safety examples

## Three Sources of Truth (to avoid drift)

1. **`packages/db/src/schema/*`** — Drizzle table definitions (raw, config, audit)
2. **`packages/metrics-catalog/catalog/`** — YAML metric definitions
3. **`packages/modules-registry/src/registry.ts`** — Module registry

Each is read by multiple systems:
- DB schema → Workers write, dbt reads, frontend queries
- Metrics catalog → dbt codegen, frontend labels, API validation
- Module registry → Workers dispatch, dbt filters, frontend nav

**Never duplicate these** in config files, environment variables, or component props.

## Naming Conventions

### Tables
- Raw: `raw.<module>_<entity_plural>` (e.g., `raw.meta_ads_ad_insights`, `raw.ghl_contacts`)
- Staging: `stg_<module>__<entity>` (e.g., `stg_meta_ads__ad_insights`)
- Mart: `mart_<business_concept>` (e.g., `mart_leads`, `mart_spend`, `mart_funnel_events`)
- Metric: `metric.<tier>_<metric_id>` (e.g., `metric.primary_cac`, `metric.custom_avg_ticket_vip`)

### Columns
- Timestamps: `<action>_at` (e.g., `created_at`, `_ingested_at`)
- Audit columns (in raw): `_ingested_at`, `_source_batch_id`, `_raw_payload`
- Soft enums: `funnel_stage` with check constraint `'topo' | 'meio' | 'fundo' | 'na'`

### Files & Folders
- TypeScript: camelCase (`createClient.ts`, `generateDbtModels.ts`)
- dbt: snake_case (`stg_meta_ads__ad_insights.sql`)
- YAML: kebab-case in filesystem, snake_case in metric `id` field

## Environment Variables

**Template-level** (for local dev):
- `DATABASE_URL` — Postgres connection string (for local testing or CI dbt runs)
- `SUPABASE_PROJECT_URL`, `SUPABASE_KEY` — for API testing

**Client-level** (per deployed instance, in Cloudflare/GitHub):
- `META_ADS_ACCESS_TOKEN`, `META_ADS_ACCOUNT_ID` — Meta Ads sync
- `GHL_API_KEY`, `GHL_LOCATION_ID` — GHL sync
- All stored in Cloudflare Secrets (referenced by Workers) and GitHub Actions Secrets

**Never commit secrets** — use `.env.example` as a template.

## Critical Constraints (Don't Violate)

1. **dbt-core runs in GitHub Actions, not Workers** — Workers cannot run Python. If you see a PR trying to run `dbt run` in a Worker, block it.
2. **Cloudflare Queues, not BullMQ+Redis** — Simpler infra. We chose this over the talentus pattern to reduce per-client deployment complexity.
3. **Config over code** — Metrics, modules, branding are all data-driven. Don't hardcode them in components.
4. **One Supabase project per client, not multi-tenant** — Each client is a clone of the template. Makes per-client backups, isolation, and scaling simpler.
5. **Raw/stg/audit schemas never exposed via PostgREST** — Only `mart` and `metric` are queryable by the frontend app. Enforce via RLS policies and by not including raw/stg in `pgrst.db_schemas`.

## Common Tasks

### Add a New Primary Metric
1. Create `packages/metrics-catalog/catalog/primary/new_metric.yml`
2. Include `sourceModels`, `sql` (aggregation), `filterSafety`, `tests`
3. Run `pnpm -F @triadeflow/metrics-catalog validate` to check YAML
4. dbt codegen (in CI) will turn it into `metric.primary_new_metric` view

### Add a Module-Specific Metric
1. Create `packages/metrics-catalog/catalog/modules/<module>/<metric>.yml`
2. Set `moduleDependency: ['<module>']` so it only materializes if module is enabled
3. Same validation + codegen process

### Add a Custom Metric (UI → YAML)
1. Client/agency fills form in dashboard
2. Saved to `config.custom_metrics` table
3. On next dbt run, codegen materializes it to `catalog/custom/<client-slug>/<id>.yml`
4. dbt picks it up and creates `metric.custom_<id>` view

### Handle a Failed Sync
1. Check `audit.sync_run_log` table for error message + which module/entity failed
2. Check `audit.freshness_check_log` to see if it exceeds `error_threshold`
3. Worker will retry automatically (backoff), but 4xx errors (auth) need manual fix (update secret)

### Deploy a Branding Change
1. Edit `config.branding_theme` row for the client (or regenerate from website URL in onboarding)
2. Next frontend deploy will pick up new CSS variables automatically (no recompile needed)

## Testing Strategy

- **Unit**: jest for utility functions, YAML validation
- **Integration**: dbt tests (singular + generic) validate schema, data quality
- **End-to-end**: local docker Postgres + dbt compile, sample metrics queries, UI sanity checks

Run locally:
```bash
pnpm test                              # all
pnpm -F @triadeflow/db test           # specific package
pnpm -F @triadeflow/metrics-catalog validate  # YAML validation
```

## FAQ for Maintainers

**Q: A client wants a metric we don't have — how fast can we add it?**
A: If it only uses existing `mart` tables, ~15 min (write YAML, validate, push). If it needs new raw data source, add the Worker sync first (~1-2h).

**Q: How do I test changes to the metrics catalog locally?**
A: Create a `catalog/custom/dev/test_metric.yml`, then `pnpm -F @triadeflow/metrics-catalog validate`. Run dbt compile dry-run to catch SQL errors.

**Q: Can we change dbt from GitHub Actions to something else?**
A: Yes, as long as the replacement can install Python/dbt-core and run on a schedule. GitLab CI, Airflow, etc. would work. Update docs/ARCHITECTURE.md if changing.

**Q: What if an upstream API (Meta Ads, GHL) changes their schema?**
A: `audit._schema_drift_log` will catch it at dbt run time. A dbt test fails, alerts the team. Update raw table schema + dbt stg model, re-run dbt.

**Q: Can I modify a metric's `sql` in production without affecting old data?**
A: Metric views are recalculated every dbt run, so yes — but `dbt_run_log` tracks what ran. If clients are caching results, they may see inconsistency. Document metric changes in PR.
